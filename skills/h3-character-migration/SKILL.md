# H3 不限时长人物迁移

把现有视频作为动作、时序、位置、镜头、构图、环境和互动来源，用一张图片中的目标角色完整替换一个明确指定的源人物。通过 `h3ctl video migrate-character` 规划 24 FPS 分段、Motion Context 续接、精确拼接和音频策略，并直接交付可播放成片。

## 适用边界

- 只处理一个明确的源人物和一个目标角色。源人物必须能按位置、服装或角色等可见特征唯一描述。
- 多人映射、固定编队、换背景或复杂舞蹈导演要求，改用 [`h3-dance-replication`](../h3-dance-replication/SKILL.md)。
- 没有源视频的原创生成、只改音频、普通剪辑或只写提示词，不走本技能。
- v1 不静默复制、删除或合并人物。需求超过单目标合同就停止并切换合适流程。

## 开始前确定合同

从当前请求和可见上下文确定以下内容；“还是刚才的视频/图片”表示可以复用当前会话中已确认的素材，不必重复追问：

- 源视频 locator：本地路径或 `asset:ID` 等远程 locator。
- 目标角色图片 locator。先实际查看图片，再描述可见身份和外观；不要从文件名猜测。
- `source_subject`：只描述要替换的那一个源人物。
- Profile、步数、LoRA、音频和输出位置。用户未指定的快速验证使用当前可用的 H3 Ref2VA Turbo profile、4 步；不要假定特定主机或模型一定存在。
- 默认音频策略为 `copy-source`，即最终完整复用源音轨。
- `--to` 使用用户可直接访问的唯一文件名；不得覆盖已有成片，除非用户明确要求。

涉及实际执行时读取 [CLI 与运行合同](references/cli-contract.md)。

## 必须先规划

1. 用 `ffprobe` 检查源视频时长、帧率、分辨率和音轨；只抽取提示词编译所需的少量代表帧。
2. 检查当前 `h3ctl` 连接、服务健康状态、Profile 和 Motion Context 能力。临时 SSH 凭据不得写入仓库、配置或交付文本。
3. 先执行同参数的 `--plan-only`。本地素材可能在解析 locator 时上传并按哈希复用，但此阶段不创建项目、不运行 GPU。
4. 核对规划不变量：窗口按时间递增；第一段拥有全部输出；后续段裁掉各自实际 overlap；所有 `owned_output_frames` 之和减去最终 trim，必须精确等于源视频的 24 FPS 帧数。
5. 尾段应优先向前移动并扩大到合法 overlap，减少或消除补帧。不能把“大量复制尾帧”当作正常方案。

规划异常、Profile 不可用、源音轨不满足所选策略或磁盘预估失败时，不提交生成。

## 提示词策略

普通迁移优先使用 `--details` 或 `--details-file`，让 CLI 自动建立稳定资源别名和完整替换关系。内容应明确：

- `<Subject 2>` 完整替换源人物；源身份不保留。
- 保留源视频的动作、姿态、时序、位置、镜头、画幅、环境、光线、构图和互动。
- 保持目标图片中实际可见的身份和外观。
- 排除源身份泄漏、混脸、变形、重复人物、闪烁和无意服装漂移。

只有用户需要完整专家提示词时才使用 `--prompt-file`，并先遵循同仓库的 [`h3-ref2va-prompt-compiler`](../h3-ref2va-prompt-compiler/SKILL.md)。迁移项目的每段源视频是运行时派生资产，因此存在额外硬约束：

- 运行时 prompt 不得预写 `<Picture N>`、`<Video N>` 或 `<Audio N>`。
- 已连接的持久图片用 `@{asset-id}`；源视频写成中性的 “the source video reference”，执行器会在每段提交时注入正确的视频绑定。
- 若目标图片尚未有 asset ID，先用默认提示词做一次 `--plan-only` 完成解析，再从 `resolved_resources` 取得 ID，编译专家 prompt 后重新规划。
- `--prompt-file` 不能与 `--details` 或 `--details-file` 同时使用。
- 当前版本的 plan/create 校验可能不完全一致；提交前主动扫描并消除上述字面媒体标签。不要因为 plan-only 通过就跳过这项检查。

本规则只影响动态派生引用。最终 H3 请求仍会得到正确的 `<Picture 1>` 与 `<Video 1>`。

## 执行和恢复

规划确认后按同一参数执行真实迁移。使用 JSONL 观察项目 ID 和阶段状态；长任务持续等待同一个项目，不因无进度百分比而重复提交。

- 普通前台执行等待所有段、合并并下载。
- `--detach` 只启动项目并返回 `project_id`。
- Ctrl-C 只中断本地等待，不代表远程项目停止。
- 通过 `project get/run/wait/merge/download` 恢复；已完成段不得重复生成。
- 第一次请求若在项目创建前被本地或 HTTP 合同拒绝，可修正后重试。项目已经创建或 job 已提交时，先查项目状态，禁止盲目重复付费任务。

运行期间给用户简短状态：当前段、完成段和是否进入 merge。不要泄露 prompt 中的内部资产 ID，除非用户正在排查接线。

## 交付

成功后确认命令完成且下载文件存在，立即用绝对路径展示并提供链接：

```markdown
![人物迁移视频](/absolute/path/output.mp4)

[下载视频](/absolute/path/output.mp4)
```

默认只交付最终成片，不自行抽帧评分或自动生成第二个 take。用户明确要求每段时，再一一交付：

- 规划中的每个源参考区间；
- 每段实际进入 concat 的生成结果，即后续段已经裁去 Motion Context 头部的版本；
- 最终合并成片。

临时帧、提示词和上传副本在成功下载后清理；保留用户原始素材、服务端持久 asset、项目恢复数据和已交付视频。素材、模型、生成结果、凭据及机器专属配置不得进入 Git。提交或推送仓库仍需用户在当前任务中明确授权。
